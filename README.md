# VENA

Сервис прогнозирования инцидентов и поддержки ремонтных работ для инженерных коллекторов Москвы. Кейс №8 «Москоллектор», хакатон «Лидеры цифровой трансформации 2026».

VENA читает журнал событий СМВУ. Модели оценивают вероятность отказа насосов и вентиляторов, неисправности и срабатывания дымовых датчиков, потери питания и затопления камер на горизонте 24–72 ч. Отдельная модель показывает, какие тревоги скорее всего не подтвердятся. Прогнозы собираются в инциденты по локации и сценарию: пожар, подтопление, потеря питания, отказ вентиляции. Диспетчер получает уведомление и черновик работы, принимает решение с причиной из справочника, и результат возвращается в журнал для дообучения. Решения остаются за диспетчером, оборудованием сервис не управляет.

## Стенд

| | |
|---|---|
| Интерфейс | https://5bit.online |
| REST API (OpenAPI) | https://5bit.online/docs |
| Проверка API | https://5bit.online/api/v1/health |
| Вход для проверки | `user1` / `0987654321` — администратор; `user2`–`user20` — диспетчеры |

Стенд работает в режиме `auto`. Если на сервер загружены журнал и справочник каналов, прогнозы строятся по реальным каналам. Если нет — те же замороженные модели оценивают синтетические каналы, и интерфейс помечает снимок как демонстрационный. Журнал СМВУ в репозиторий не входит.

## Архитектура

```
браузер ─HTTPS─▶ Caddy ─┬─▶ frontend  Next.js 16, React 19
                        └─▶ backend   FastAPI ─▶ PostgreSQL 16
                                 │  ▲
                   пакеты потока │  │ snapshot.json каждые 30 с
                                 ▼  │
                            ml-worker  замороженные модели CatBoost / LightGBM / LogReg
                                 ▲
             журнал СМВУ + справочник каналов (CSV/XLSX, API)
```

1. **ML-контейнер** строит по каждому каналу признаки на момент последнего события, применяет модели и калибровку и атомарно публикует снимок прогнозов. В режиме потока он пересчитывает только каналы из нового пакета событий, раз в сутки — всё.
2. **Backend** забирает новый снимок и группирует прогнозы уровней `critical` и `attention` в инциденты. По каждому инциденту создаются уведомление (в интерфейсе и по почте) и черновик работы. Работы, решения, история оценок, пользователи, аудит и очередь писем хранятся в PostgreSQL.
3. **Интерфейс** показывает, что требует внимания, где и почему. Через него диспетчер ведёт работу до результата.

Подробно: [docs/architecture.md](docs/architecture.md).

## Модели

Качество на первом полугодии 2026 года. Этот период не использовался ни для обучения, ни для подбора параметров. Протокол и все проверенные подходы описаны в [ml/README.md](ml/README.md), значения — в `ml/results/models.json`.

| Модель | Что прогнозирует | Алгоритм | Доля событий | AP | ROC AUC |
|---|---|---|---|---|---|
| `pump_24h`, `pump_72h` | отказ насоса за 24 / 72 ч | смесь LogReg + LightGBM | 0.117 / 0.259 | 0.329 / 0.508 | 0.689 / 0.659 |
| `fan_24h`, `fan_72h` | отказ вентилятора за 24 / 72 ч | CatBoost | 0.042 / 0.092 | 0.240 / 0.540 | 0.879 / 0.922 |
| `smoke_24h` | неисправность дымового датчика за 24 ч | CatBoost | 0.009 | 0.271 | 0.930 |
| `smoke_alarm_24h` | срабатывание дымового датчика за 24 ч | CatBoost | 0.018 | 0.218 | 0.858 |
| `phase_24h` | потеря питания за 24 ч | CatBoost | 0.253 | 0.751 | 0.874 |
| `flood_24h` | затопление камеры насосной за 24 ч | LightGBM | 0.086 | 0.254 | 0.701 |
| `alarm_30m` | подтверждение тревоги за 30 мин (без серий ППР) | LightGBM | 0.792 | 0.909 | 0.739 |
| `object_power_24h` | отключение питания объекта по реестру за сутки | LightGBM по истории и состояниям объекта | 0.535 | 0.840 | 0.841 |
| `object_flood_24h`, `object_flood_6h` | подтопление станции по реестру за сутки / 6 ч | LightGBM | 0.068 / 0.021 | 0.280 / 0.185 | 0.838 / 0.841 |
| `object_fire_24h` | пожарный инцидент объекта по реестру за сутки | LightGBM | 0.019 | 0.214 | 0.837 |

AP сравнивается с долей событий: при случайном ранжировании AP равна этой доле. Вероятности откалиброваны изотонической регрессией, ECE 0.004–0.038. Рабочие точки:

- потеря питания: при precision 0.70 recall 0.58 по каналам и 0.91 по объектам (модель объекта);
- реальные инциденты 2026H1, за 6 ч до начала объект в топ-3 модели объекта: подтопления — 65 % (случайно 17 %), пожарные — 56 % (случайно 12 %); отключения питания — 28 % по списку каналов (случайно 16 %);
- насосы: из пяти насосов с наибольшим риском `pump_72h` в сутки 76 % начинают отказ в течение 72 ч;
- прогноз числа инцидентов на неделю: ошибка 13 % для потери питания, 38 % для затопления камер;
- 71 % тревог 2026H1 — серии планово-предупредительных работ (5 и более извещателей объекта за 10 минут в рабочее время), они помечаются отдельно.

## Сверх ТЗ

- **Индекс здоровья** 0–100 для объекта и секции: откалиброванная вероятность события за сутки и её динамика по дням.
- **Отделение серий ППР** от реальных тревог и модель подтверждения тревоги за 30 мин.
- **Нагрузка тревог по ISA-18.2 / EEMUA 191**: активации в час, лавины, «дребезжащие» каналы.
- **Схема питания** объекта: фидеры, шина, потребители и каскад — что остановится при отключении ввода.
- **Причины прогноза** простым языком по вкладам признаков (SHAP) в каждую оценку.
- **Прогноз против факта**: прогнозы, выданные после конца журнала, сверяются с поступающими событиями (`GET /ml/prospective`).
- **Отчёт смены** в один клик: что предсказали, что произошло, что сделано.
- **Проверка качества журнала** по справочнику состояний: сверка названий, сбойные даты, флаг «тревожное», показания газоанализаторов вне диапазона.
- **Машина времени**: администратор воспроизводит неделю журнала через поток СМВУ, симуляция диспетчера принимает решения по черновикам, «Эффект» и прогноз против факта заполняются настоящими цифрами — по каналам и по моделям объекта. Прогон 03–06.06.2026: точность топ-3 утреннего списка питания 78 %, у 5 из 7 подтоплений станция в топ-3, тревоги по питанию подтвердились в 87 % случаев, симуляция — 93 подтверждения и 31 отклонение ([demo.md](docs/demo.md)).
- **Учебные сценарии из реальных инцидентов**: события пожара, подтопления или отключения питания из журнала 2026H1 повторяются в потоке со сдвигом во времени; видно, за сколько часов объект попал в утренний список.
- **Реестр инцидентов и модели объекта**: правила превращают журнал состояний в события объекта, модели обучены на этих событиях; экран «Инциденты» — утренний список объектов и последние инциденты реестра.
- **«Взять в работу»**: диспетчер закрепляет ситуацию за собой, остальные видят, кто её ведёт; действия в аудите.
- **Бизнес-порог**: калькулятор окупаемости утреннего списка по точке безубыточности ([business.md](docs/business.md)).
- **Эксплуатация**: автодеплой из `main` с резервной копией, smoke-проверкой и откатом, очередь писем с повторами, проверка загрузок до применения.

## Ограничения

- Прогнозируется состояние канала в журнале, а не подтверждённый физический отказ. Меток реальных пожаров и проникновений в данных нет: пожар и подтопление определены правилами реестра, которые нужно согласовать с заказчиком.
- Нет реальных координат объектов: карта строится по условной геометрии из реестра, пока заказчик не загрузит GeoJSON или WKT.
- Подключение к каталогу LDAP/AD, учётной системе оборудования и системе заявок заказчика реализовано, но требует их адресов и учётных данных.
- Период 2026H1 использовался для выбора между двумя-тремя кандидатами, поэтому его метрики немного оптимистичны. Независимая проверка — сверка прогнозов после конца журнала.

## Локальный запуск

```bash
docker compose up -d --build
```

Команда собирает и запускает PostgreSQL, ML-воркер, backend и интерфейс. Первая сборка занимает около 10 минут, повторный запуск — около минуты. Когда `docker compose ps` показывает все сервисы `healthy`, откройте http://localhost:3100 и войдите как `user1` / `0987654321` — администратор, `user2`–`user20` с тем же паролем — диспетчеры. API — http://localhost:8100/docs.

Если до запуска положить журнал (`ext-journal-*.csv` и `справочник_каналов_датчиков.csv`) в `ml/dataset`, ML-контейнер посчитает прогнозы по реальным каналам. Без журнала он публикует демонстрационный снимок тех же замороженных моделей. Порты, каталоги и переменные описаны в [docs/installation.md](docs/installation.md#локальный-запуск-в-docker), production-развёртывание — в [infra/README.md](infra/README.md).
