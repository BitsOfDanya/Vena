# Архитектура

## Назначение

VENA прогнозирует инциденты в инженерных коллекторах по журналу событий СМВУ и помогает диспетчеру принимать
решения о ремонтных работах. Сервис не управляет оборудованием и не принимает решений за диспетчера.

## Функциональные блоки

| Блок | Что делает | Экраны и API |
|---|---|---|
| Прогноз по каналам | модели на 24 и 72 ч, изотоническая калибровка, причины прогноза, срок до отказа насоса | `/pulse`, `/api/v1/predictions` |
| Модели объекта | подтопление за 6 и 24 ч, пожар, отключение питания на объекте | `/incidents`, `/api/v1/incidents/objects` |
| Ситуации и тревоги | группировка прогнозов по локации и сценарию, подтверждение тревог, проверка доступа | `/api/v1/situations`, `/alarms` |
| Уведомления | правила с паузами повторов, эскалация, почта | [email-notifications.md](email-notifications.md) |
| Работы, решения, журнал | черновик работы на инцидент, решение с причиной, исход; пары «прогноз → исход» для дообучения | `/actions`, `/journal`, `/api/v1/ml/feedback` |
| Аналитика и отчёты | индекс здоровья 0–100, сезонность, погода, эффект, отчёты PDF/XLSX, выгрузка CSV/XML | `/dashboard`, `/api/v1/analytics/*`, `/api/v1/reports/*` |
| Карта, машина времени, доступ | геослой GeoJSON/WKT; проигрывание журнала как потока; [роли и области](authentication.md) | `/network`, `/api/v1/spatial`, `/api/v1/replay` |

## Компоненты

```
 браузер ──HTTPS──▶ Caddy :443 ──┬── /api/*, /docs ──▶ backend :8000 (FastAPI, APScheduler)
                                 └── остальное ─────▶ frontend :3000 (Next.js)

 СМВУ ──▶ POST /api/v1/smvu/events ──▶ backend ──▶ PostgreSQL 16 (события, import_outbox)
                                          │ каждые 10 с
                                          ▼
                              том inbox: stream-<id>.jsonl
                                          │ каждые 30 с
                                          ▼
 том dataset: журнал, справочники ──▶ ml-worker: признаки → модели → калибровка
                                          │ атомарная замена файла
                                          ▼
                              том predictions: snapshot.json
                                          │ только чтение, каждые 30 с
                                          ▼
                 backend: история оценок, инциденты, уведомления, черновики работ
                                          │ REST /api/v1
                                          ▼
                 интерфейс: решение диспетчера, исход работы ──▶ PostgreSQL 16
                                          │ /api/v1/journal, /api/v1/ml/feedback
                                          ▼
                 ml/run_production_refresh.py: переобучение моделей
```

| Компонент | Технологии | Порт | Ответственность |
|---|---|---|---|
| `caddy` (только стенд) | Caddy 2 | 80, 443 | TLS, `/api/*`, `/docs`, `/redoc`, `/openapi.json` → backend, остальное → frontend |
| `frontend` | Next.js 16, React 19, TanStack Query | 3000 (локально 3100) | интерфейс; слои FSD `app → views → widgets → features → entities → shared` |
| `backend` | FastAPI, SQLAlchemy 2, Alembic, APScheduler | 8000 (локально 8100) | API, приём снимка и потока, инциденты, уведомления, работы, права, аудит |
| `db` | PostgreSQL 16 | 5432 (локально 127.0.0.1) | оперативные данные и история |
| `ml` (ml-worker) | Python 3.12, pandas, LightGBM, CatBoost | — | `infra/scripts/ml-worker.py`: режимы `VENA_ML_MODE` `demo`, `journal`, `auto` |
| `helpdesk`, `ldap` (только локально) | FastAPI; OpenLDAP | 8090; 389 | эмуляторы системы заявок с реестром оборудования и каталога LDAP |

## Потоки данных

1. **Поток событий.** `POST /api/v1/smvu/events` (JSON или XML) сохраняет события и запись в `import_outbox`, задание
   раз в 10 с выкладывает пакет в том inbox. Загруженный через интерфейс журнал публикуется в том dataset (`uploads/`).
2. **Расчёт.** `ml/stream_scoring.py` раз в `VENA_STREAM_POLL_SECONDS` пересчитывает каналы с новыми событиями (полностью — раз
   в 24 ч и при смене журнала) и пишет `snapshot.json` через `os.replace`; без журнала — демо-снимок `score_snapshot.py --demo`.
3. **Приём снимка.** Backend раз в `VENA_PREDICTION_REFRESH_SECONDS` читает снимок; каждый `snapshot_id` обрабатывается
   один раз (`processed_snapshots`), прогнозы `critical` и `attention` группируются в инциденты.
4. **Решение и обратная связь.** Диспетчер подтверждает работу или отклоняет её с причиной, закрытие фиксирует исход.
   `ml/run_production_refresh.py` переобучает модели и возвращает прежнюю версию, если PR-AUC падает больше чем на 0,005.
5. **Машина времени.** `/api/v1/replay` пишет `control.json` в том inbox, воркер пересобирает историю до выбранного момента.

## Хранение

PostgreSQL хранит пользователей и сессии, уведомления, работы, решения, историю оценок, настройки, очередь писем, аудит, геослой
и реестр оборудования (копия — `infra/scripts/backup.sh` по таймеру `infra/systemd/vena-backup.timer`). Тома: `dataset` (журналы
и справочники CSV, вне Git), `inbox` (JSONL), `predictions` (снимок). В образах — модели `ml/artifacts/models` и витрины `ml/results`.

## Безопасность

- На стенде наружу открыт только Caddy (80, 443) с автоматическим сертификатом, PostgreSQL — во внутренней сети `database`.
- JWT в HttpOnly-cookie или Bearer, сессии в БД, роли и области видимости проверяются на сервере на каждом запросе.
- Аудит (`/api/v1/audit`, роль `admin`): вход и выход, изменения работ, уведомлений, настроек, пользователей, импорт, поток.
- Снимок прогнозов монтируется в backend только для чтения, образы стенда для backend и frontend запускаются не от root.
  Секреты (JWT, SMTP, LDAP, PostgreSQL) задаются переменными окружения и не хранятся в Git и БД.
