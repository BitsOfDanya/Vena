# Архитектура

## Назначение

VENA прогнозирует инциденты в инженерных коллекторах по журналу событий СМВУ и поддерживает решения диспетчера по ремонтным работам. Сервис не управляет оборудованием и не принимает решений за диспетчера (ТЗ, раздел 5).

## Функциональная архитектура

Контур диспетчера: **прогноз → инцидент → уведомление → решение → работа → результат → обратная связь модели**.

                 ┌──────────────────────▼───────────────────────┐
                 │ backend/ FastAPI                              │
                 │  PredictionSource ─▶ ingest ─▶ incidents      │

                 ┌───────────▼─────────┐  ┌─────────▼────────────┐

| Компонент | Технологии | Ответственность |
|---|---|---|
| `ml/` | Python 3.12, pandas, DuckDB, LightGBM, CatBoost, scikit-learn | извлечение событий, признаки, обучение, заморозка моделей, снимок прогнозов |
| `backend/` | FastAPI, SQLAlchemy 2, Alembic, APScheduler, psycopg 3 | API, ingest прогнозов, инциденты, уведомления, работы, журнал, RBAC, аудит |
| `frontend/` | Next.js 16, React 19, TanStack Query, Tailwind 4, zod | интерфейс диспетчера и руководителя |
| `db` | PostgreSQL 16 | уведомления, работы и их история, решения, история прогнозов, настройки, аудит, геослой |

Слои фронтенда — Feature-Sliced Design: `app → views → widgets → features → entities → shared`.

## Потоки данных

1. **Скоринг.** `ml/score_snapshot.py` загружает артефакты `ml/artifacts/models`, строит признаки каждого канала в момент его последнего события и пишет `ml/results/predictions/snapshot.json`. Снимок содержит откалиброванную вероятность, уровень риска, сценарий, тег локации и факторы, а также оценки тревог за 30 дней и события доступа для проверки.
2. **Ingest.** Бэкенд читает снимок только на чтение. Новый снимок обрабатывается один раз (`processed_snapshots`): сохраняется история оценок (`prediction_points`), считается изменение относительно прошлого снимка, прогнозы уровней critical/attention группируются в инциденты, по каждому инциденту создаются уведомление и черновик работы. Повтор в пределах cooldown подавляется.
3. **Решение.** Диспетчер подтверждает черновик (выезд бригады) или отклоняет его с причиной из справочника. Причина сохраняется как исход обратной связи.
4. **Результат.** Закрытие работы фиксирует исход: подтверждён инцидент, выполнено ТО, норма, мониторинг, ложное срабатывание.
5. **Поток.** СМВУ передаёт события в `POST /api/v1/smvu/events`; API кладёт батч в общую папку, ML-воркер пересчитывает каналы с новыми событиями и публикует снимок, backend забирает его каждые 30 с. Прогнозы, выданные после конца журнала, сверяются с фактом по мере поступления событий (`/api/v1/ml/prospective`).
6. **Обратная связь.** `/api/v1/journal` и `/api/v1/ml/feedback` выдают размеченные пары «прогноз → исход» для дообучения.

## Хранение

| Контур (ТЗ, раздел 13) | Где |
|---|---|
| Оперативный | PostgreSQL: открытые инциденты, уведомления, работы |
| Архив | PostgreSQL: история оценок, решения, результаты, аудит; журналы СМВУ — исходные CSV вне репозитория |
| Аналитические витрины | `ml/results/`: таблицы экспериментов, `directions.json`, снимок прогнозов |

## Безопасность

- RBAC: роли `viewer` (чтение), `dispatcher` (решения и работы), `admin` (настройки, аудит). Аутентификация — email/логин и пароль с Argon2-хешем. JWT передаётся в HttpOnly cookie или `Authorization: Bearer`. Сессии хранятся в БД и отзываются при выходе; роль и активность проверяются по БД на каждом запросе.
- Все изменяющие действия пишутся в audit log (`/api/v1/audit`).
- Интеграция с источниками — только чтение: ML-каталоги монтируются в контейнер API в режиме `ro`.
- Секреты SMTP и подписи JWT задаются переменными окружения и не хранятся в БД.
- TLS терминируется на ingress / reverse proxy перед сервисом; в compose не входит.
- LDAP/AD: защищённый bind, группы → роли, JWT; [настройка](data-integrations.md).
