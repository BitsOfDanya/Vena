# Почтовые уведомления Vena

SMTP настраивается в `/opt/vena/shared/.env` (права `0600`). Секреты не добавляются в Git и не передаются браузеру.

```dotenv
SMTP_HOST=smtp.resend.com
SMTP_PORT=587
SMTP_SECURE=false
SMTP_TLS=true
SMTP_USER=resend
SMTP_PASSWORD=<ключ Resend>
SMTP_FROM='UFranshize <no-reply@ufranshize.site>'
```

`SMTP_SECURE=false` означает отсутствие немедленного TLS при соединении; на порту 587 затем выполняется обязательный STARTTLS с проверкой сертификата. Для порта 465 используйте `SMTP_SECURE=true`. `SMTP_USERNAME` и `VENA_SMTP_USERNAME` поддерживаются для совместимости. Отдельный `RESEND_API_KEY` приложению не нужен: используется SMTP. Домен отправителя должен быть подтверждён в Resend. [Документация провайдера](https://resend.com/docs/send-with-smtp).

## Получатели и правила

Администратор открывает **Настройки → Уведомления**, вводит рабочие адреса в группы, выбирает получателей и канал «По почте» для правил и нажимает «Сохранить настройки». Пустые и отключённые группы не получают писем. Демо-адреса пользователей не используются автоматически. Там же доступны проверочное письмо на явно указанный адрес и журнал доставки.

По умолчанию включены почтовые правила:

- новые события — одно уведомление на принятый пакет потока либо загрузку исторического журнала;
- тревожные события (`alarm=true`) — отдельное уведомление, пауза повторов 15 минут по каналу; для пакета нескольких каналов пауза общая;
- критический прогноз — пауза 4 часа;
- нежелательный прогноз на горизонте 24 часа — пауза 6 часов;
- новая коррелированная связка — пауза 2 часа.

Пакет с тревожными событиями получает одно тревожное уведомление вместо отдельного обычного письма. Повторно принятые идентификаторы событий не создают новых писем. Исторический импорт отправляет сообщение о загрузке, а не отдельное аварийное письмо на каждую старую строку. Модельные письма отправляются только для источника `journal`. Демонстрационные прогнозы не рассылаются; утренняя сводка также пропускается при демонстрационном снимке. Правила назначенных/просроченных работ и недоступности источника сохранены для соответствующих производителей уведомлений; само включение правила не создаёт события.

## Очередь и диагностика

Уведомление и его письма сохраняются в одной транзакции PostgreSQL. SMTP вызывается после фиксации данных фоновым заданием каждые 10 секунд. Очередь переживает перезапуск приложения. При ошибке выполняется до шести попыток с паузами 1, 2, 4, 8 и 16 минут. После шестой ошибки запись получает статус `failed`; автоматических бесконечных повторов нет. Для Resend используется стабильный `Resend-Idempotency-Key` (защита повторной отправки при сбое между SMTP и фиксацией результата в базе в пределах срока хранения ключа у провайдера). Для иных SMTP действует доставка как минимум один раз: редкий повтор при таком сбое возможен.

`GET /api/v1/integrations/email/deliveries` доступен только администратору: последние 50 записей, количество ожидающих/ошибочных писем, число попыток и время. Статус `sent` означает **принято SMTP**, а не подтверждённое получение или прочтение адресатом. Доставку и возвраты проверяют в Resend. Ответы SMTP с потенциальными секретами не сохраняются в журнале — только класс ошибки.

Утренняя сводка также проходит через очередь. Время и часовой пояс задаются настройками `digest`; `VENA_DIGEST_ENABLED=false` отключает её на уровне сервера. Изменение времени расписания через API требует перезапуска backend; переключатель включения применяется сразу.

Очередь включена в обычный PostgreSQL backup. Проверки: `backend/tests/test_email_delivery.py` покрывает откат транзакции, повторную доставку, исчерпание попыток, устранение повторов, отключённые группы, права доступа, TLS/SMTPS и реальный SMTP-обмен с изолированным локальным приёмником.
