# Почтовые уведомления

Почта — второй канал уведомлений после колокольчика в интерфейсе. Письма отправляет backend по SMTP через очередь в PostgreSQL: отправка переживает перезапуск, повторяется при ошибке и не блокирует запросы API.

## Настройка SMTP

Параметры задаются переменными окружения backend. На стенде это `/opt/vena/shared/.env` (права `0600`), локально — окружение `compose.yaml` или `backend/.env`. В Git и в браузер секреты не попадают.

```dotenv
SMTP_HOST=smtp.example.org
SMTP_PORT=587
SMTP_USER=vena
SMTP_PASSWORD=<пароль или API-ключ провайдера>
SMTP_FROM='VENA <no-reply@example.org>'
SMTP_TLS=true
SMTP_SECURE=false
```

| Переменная | Назначение |
|---|---|
| `SMTP_HOST`, `SMTP_FROM` | обязательны; без любой из них канал email выключен, уведомления остаются только в интерфейсе |
| `SMTP_PORT` | 587 (STARTTLS) или 465 (SMTPS) |
| `SMTP_USER`, `SMTP_PASSWORD` | вход на SMTP-сервер; без `SMTP_USER` отправка идёт без авторизации |
| `SMTP_TLS=true` | STARTTLS с проверкой сертификата сервера |
| `SMTP_SECURE=true` | TLS сразу при подключении (порт 465) |

Также принимаются имена с префиксом `VENA_` (`VENA_SMTP_HOST` и т. д.) и `SMTP_USERNAME` вместо `SMTP_USER`. Подходит любой SMTP-сервер: корпоративный релей или облачный провайдер. Домен отправителя должен быть подтверждён у провайдера. Для Resend в письмо добавляется `Resend-Idempotency-Key`, чтобы исключить повторную отправку.

Проверка: **Настройки → Уведомления → Проверочное письмо** (роль `admin`) или `POST /api/v1/notifications/test`. Состояние канала: `GET /api/v1/integrations/email/status`.

## Получатели и правила

Получатели задаются группами: «Диспетчерская», «Эксплуатация», «Руководство». Администратор вводит адреса в **Настройки → Уведомления**, для каждого правила выбирает группы и каналы («В интерфейсе», «По почте») и сохраняет. Пустые и отключённые группы писем не получают. Настройки хранятся в PostgreSQL (`PUT /api/v1/settings/notifications`).

| Правило | Когда срабатывает | Уровень | Пауза повторов |
|---|---|---|---|
| Новые события | принят пакет потока СМВУ или загружен исторический журнал | info | нет |
| Тревожное событие | в пакете есть события с `alarm=true` | attention | 15 мин на канал |
| Критический прогноз | новый снимок моделей дал инцидент уровня `critical` | critical | 4 ч |
| Прогноз на 24 ч | инцидент уровня `attention` на горизонте 24 ч | attention | 6 ч |
| Новая связка | уведомление о коррелированной группе, созданное через API | attention | 2 ч |

Правила обрабатываются так:

- Пакет с тревожными событиями даёт одно тревожное письмо вместо обычного. Повторно принятые идентификаторы событий новых писем не создают.
- Исторический импорт даёт одно письмо о загрузке, а не письмо на каждую старую тревогу.
- Письма о прогнозах отправляются только для снимка по реальному журналу (`data_source=journal`). Демонстрационный снимок не рассылается.
- За один пересчёт создаётся не более `VENA_PREDICTION_CRITICAL_LIMIT` (20) уведомлений на сценарий.

**Утренняя сводка.** Письмо в заданное время со сводкой по прогнозам и работам. Время и часовой пояс задаются в блоке «Сводка» тех же настроек. `VENA_DIGEST_ENABLED=false` отключает сводку на сервере. Новое время начинает действовать после перезапуска backend, переключатель «включено» — сразу.

## Очередь доставки

1. Уведомление и его письма (`delivery_log`) сохраняются в одной транзакции.
2. Фоновое задание каждые 10 с забирает ожидающие письма (`SELECT … FOR UPDATE SKIP LOCKED`) и отправляет их по SMTP.
3. При ошибке следует повтор через 1, 2, 4, 8 и 16 мин. После шестой неудачи письму ставится статус `failed`.
4. `sent` означает, что письмо принято SMTP-сервером. Доставку до ящика и возвраты подтверждает журнал провайдера.

Журнал доставки: **Настройки → Уведомления** или `GET /api/v1/integrations/email/deliveries` (только `admin`). Там видны последние 50 писем, счётчики по статусам и число попыток. Ответы SMTP не сохраняются, в журнал пишется только класс ошибки, потому что в ответах бывают адреса и учётные данные. Очередь входит в резервную копию PostgreSQL.

## Ограничения

- Правила «Работа назначена», «Работа просрочена» и «Источник недоступен» есть в настройках, но backend пока не формирует для них события.
- Каналы webhook, Telegram и Teams показаны в интерфейсе как планируемые, отправки по ним нет.
- Пока SMTP не настроен, письма накапливаются в очереди со статусом `pending` и уходят после настройки.

Тесты: `backend/tests/test_email_delivery.py`. Покрыты откат транзакции, повторная доставка, исчерпание попыток, дедупликация, отключённые группы, права доступа, STARTTLS/SMTPS и обмен с локальным SMTP-приёмником.
