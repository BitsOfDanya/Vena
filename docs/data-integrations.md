# Загрузка данных и корпоративные интеграции

## Журнал и справочник через интерфейс

Администратор открывает **Настройки → Интеграции** (`/settings/integrations`).
Сначала выберите «Справочник каналов», скачайте шаблон и загрузите CSV или XLSX.
После проверки появятся номера ошибочных строк и кнопка «Применить загрузку».
Ни одна строка ошибочного файла не применяется. История показывает число строк,
добавленных, обновлённых и уже существующих записей. Затем загрузите журнал тем же способом.

CSV: UTF-8 (допускается BOM), разделитель — запятая, точка с запятой или табуляция.
XLSX: один лист, первая строка — заголовки, без формул и макросов. Идентификаторы
храните как текст, чтобы Excel не терял начальные нули. Максимум — 256 МБ и
1 000 000 строк; большие журналы разбивайте на части. Распакованный XLSX также
ограничен 256 МБ. Предпросмотр показывает первые 100 ошибок; счётчик учитывает все.

Обязательные колонки справочника:

| Колонка файла | Поле API | Смысл |
|---|---|---|
| ид_канала_данных | asset_id | Стабильный идентификатор канала, до 32 символов |
| название_датчика | name | Название оборудования |
| тип_датчика | equipment_type | Тип из справочника СМВУ |
| тег_инженерной_системы | tag | Тег локации |
| тип_инж_системы | system_type | Инженерная система |
| ид_объект | object_id | Идентификатор объекта, не извлекается из названия |

Дополнительные поля API/файла: external_id (по умолчанию равен каналу), section,
manufacturer, model, serial_number, installed_on (YYYY-MM-DD), status
(active/maintenance/retired). Отсутствующие в выгрузке записи **не удаляются**;
вывод из эксплуатации задаётся явно через status=retired. Один внешний идентификатор
не может незаметно переехать на другой канал. Новое имя/объект/секция обновляются
сразу в БД и дереве `/assets/tree`; каналы без расчёта показывают «Нет прогноза».

Журнал соответствует приложению 1 ТЗ: ид_события, ид_канала_данных, дата (YYYY-MM-DD),
время (HH:MM:SS), тревожное (t/f, true/false, 1/0, да/нет), значение_датчика.
Альтернатива API: event_id, channel_id, ts (ISO 8601), alarm, value.
Время без зоны трактуется в VENA_TIMEZONE (по умолчанию Europe/Moscow).
Неизвестные каналы отклоняются. Повтор существующего события не дублируется;
совпадающий event_id с другим содержимым отклоняет всю загрузку.

API для администратора:

- `POST /api/v1/imports?kind=channels|journal`: multipart/form-data, поле file; проверка и ID загрузки.
- `POST /api/v1/imports/{id}/apply`: атомарное применение; повтор запроса безопасен.
- `GET /api/v1/imports/template/{kind}.xlsx`: шаблон.
- `GET /api/v1/integrations/status`: состояние источника, счётчики, очередь публикаций и история.
- `GET /api/v1/equipment?offset=0&limit=50&q=...`: реестр с поиском.
- `PUT /api/v1/equipment`: JSON `{"items":[...]}`, обновление справочника без пересборки.

## Передача в ML и поток

В production backend имеет доступ на запись к `/srv/ml/dataset`, смонтированному из
`/opt/vena/shared/dataset`. UID 10001 должен иметь право записи. Секреты интеграций
хранятся только в серверном `.env`, сертификаты — в `/opt/vena/shared/certs`.

После транзакции БД очередь публикаций обновляет CSV/справочник и `.revision`.
При сбое публикация повторяется через 10 секунд. `VENA_ML_MODE=auto` ждёт реальные
файлы, следит за изменениями и перезапускает расчёт без пересборки контейнера.
Кэш извлечённых событий пересоздаётся. Сначала нужен полный расчёт истории;
на больших журналах он занимает десятки минут. Для модели нужно минимум 20 событий
канала и поддерживаемый тип датчика. Загрузка справочника сама по себе не создаёт
прогнозы. Обученные модели при импорте не переобучаются.

`demo` помечается в API и интерфейсе. `auto` без журнала показывает демонстрационный
снимок с `data_source=demo` и переключается на реальные каналы, как только журнал обработан. Проверяйте `data_source=journal`,
ID каналов в `/predictions`, `worker.state` и состояние снимка; исторический срез
не выдаётся за наблюдения текущего дня.

Новые события: `POST /api/v1/smvu/events` с JWT диспетчера/администратора,
`batch_id`, `event_count`, `events` (`event_id`, `channel_id`, `ts`, `value`, `alarm`).
Тот же пакет принимается в XML с `Content-Type: application/xml`:

```xml
<batch id="smvu-0001" event_count="2" last_event_at="2026-07-01T09:05:00">
  <event event_id="1" channel_id="96463" ts="2026-07-01T09:00:00" alarm="true">Неисправен</event>
  <event event_id="2" channel_id="96463" ts="2026-07-01T09:05:00">Норма</event>
</batch>
```

XML сводится к той же модели, что JSON: те же проверки, лимиты, ответы и аудит. Разбор —
defusedxml: DTD, сущности, внешние ссылки и любые элементы, кроме `<batch>` и `<event>`,
отклоняются с 422.
ML опрашивает очередь каждые 30 секунд и пересчитывает затронутые каналы.
Смотрите `/predictions/snapshot`: `stream.events`, `channels_rescored`,
`published_at`, `latency_seconds`. Архив обработанных батчей сохраняется в inbox/processed
и восстанавливается при перезапуске; одинаковые события устраняются перед расчётом.
`/ml/prospective` сравнивает выданные прогнозы с последующими событиями.

`infra/scripts/verify-stream.py` проверяет CSV → справочник с ид_объект → прогноз →
новое событие → пересчёт на **изолированных синтетических тестовых данных**.
Его успешность не означает подключения журнала заказчика.

## Синхронизация с учётной системой (ТЗ 10)

Коннектор выполняет только GET; данные заказчика не изменяются. Протокол источника
в ТЗ не определён: реализован HTTPS JSON API с Bearer-токеном и пагинацией по cursor.
Для 1С/OData или другой схемы нужен согласованный endpoint/адаптер, а не произвольный
URL формы входа. Без параметров коннектор честно сообщает «не настроено».

Серверные переменные:

```dotenv
VENA_EQUIPMENT_SYNC_ENABLED=true
VENA_EQUIPMENT_SYNC_URL=https://accounting.example/api/equipment
VENA_EQUIPMENT_SYNC_TOKEN=replace-on-server
VENA_EQUIPMENT_SYNC_SOURCE=customer
VENA_EQUIPMENT_SYNC_INTERVAL_SECONDS=900
VENA_EQUIPMENT_SYNC_FIELD_MAP={}
```

Ответ — массив записей EquipmentIn или объект `{"items":[...],"next_cursor":"..."}`.
Конец — отсутствующий/null next_cursor. Следующий GET передаёт `?cursor=...`.
Обязательные поля JSON: asset_id, external_id, name, object_id; для ML также нужны
правильные equipment_type, tag, system_type. Идентификаторы — строки.
Пример маппинга полей: `{"asset_id":"channel.id","external_id":"id","name":"title","object_id":"object.id"}`.
Остальные требуемые поля нужно добавить в этот же маппинг.

Лимиты: 20 секунд на сетевую операцию, 10 МБ/страницу, 100 страниц, 100 000 каналов.
Редиректы запрещены; сертификат проверяется. Для внутреннего CA задайте
VENA_EQUIPMENT_SYNC_CA_FILE=/srv/certs/customer-ca.pem. HTTP разрешается только
явной VENA_EQUIPMENT_SYNC_ALLOW_HTTP=true для изолированного тестового контура.
При сетевой ошибке/некорректных данных реестр сохраняется без частичного обновления;
ошибка отражается в истории без токенов. Параллельные изменения сериализуются в БД.
Ручной запуск — кнопка «Синхронизировать реестр» или POST /equipment/sync.

## Система учёта заявок (ТЗ 6)

Утверждённая работа уходит заявкой во внешнюю систему, статус заявки возвращается в историю
работы. Протокол источника в ТЗ не задан: реализован HTTPS JSON API с Bearer-токеном из двух вызовов.

- `POST {VENA_HELPDESK_URL}/tickets` с `external_ref` (ID работы), `title`, `description`,
  `priority` (`high`/`medium`/`low`), `due_at` (ISO 8601) → `{"id": …, "status": …}`. В описании —
  причина, объект, канал с названием из реестра, приоритет и срок. `external_ref` — ключ
  идемпотентности: повтор для той же работы должен вернуть существующую заявку.
- `GET {VENA_HELPDESK_URL}/tickets/{id}` → `{"id": …, "status": …}`.

Заявка создаётся при утверждении черновика и при создании работы сразу запланированной.
Если система недоступна, работа сохраняется как обычно, заявка получает статус `pending`, и
отправку повторяет планировщик. Он же раз в `VENA_HELPDESK_INTERVAL_SECONDS` (60 с) опрашивает
незакрытые заявки. Каждое изменение пишется в историю работы: «Заявка №12: принята».
Статусы: `new` — зарегистрирована, `accepted` — принята, `in_progress` — в работе,
`closed` — закрыта; другие значения записываются как есть. Закрытие заявки не закрывает
работу: результат фиксирует диспетчер. В API работ — поля `helpdesk_ticket_id` и
`helpdesk_status`, создание заявки — в аудите (`helpdesk.ticket`).

```dotenv
VENA_HELPDESK_URL=https://servicedesk.example/api
VENA_HELPDESK_TOKEN=replace-on-server
VENA_HELPDESK_INTERVAL_SECONDS=60
VENA_HELPDESK_CA_FILE=/srv/certs/customer-ca.pem
```

Пустой `VENA_HELPDESK_URL` выключает интеграцию; в production он пуст, пока заказчик не
передаст адрес и токен. Требования к соединению те же, что у учётной системы: только HTTPS
(HTTP — явной `VENA_HELPDESK_ALLOW_HTTP=true`), без редиректов, проверка сертификата,
5 секунд на запрос. Для системы с другой схемой API нужен адаптер к этим двум вызовам.

## Эмуляторы внешних систем

По решению заказчика внешние взаимодействия проверяются на шаблонах и эмуляторах.
Корневой `compose.yaml` поднимает их вместе с сервисом.

| Сервис | Что эмулирует | Адрес |
|---|---|---|
| `helpdesk` | систему заявок и учётную систему оборудования, `emulators/helpdesk` | http://localhost:8090 (`VENA_HELPDESK_PORT`), в сети compose — http://helpdesk:8090 |
| `ldap`, профиль `ldap` | каталог OpenLDAP с тремя пользователями | ldap://ldap:389, StartTLS; [authentication.md](authentication.md#тестовый-каталог-ldap) |

Эмулятор заявок — FastAPI без БД, заявки хранятся в JSON в томе `vena-helpdesk`.
`POST /tickets`, `GET /tickets/{id}`, `GET /tickets?status=…`. Статус меняется со временем:
принята через `HELPDESK_ACCEPT_SECONDS` (60), в работе через `HELPDESK_START_SECONDS` (180),
закрыта через `HELPDESK_CLOSE_SECONDS` (600). Backend локального стенда подключён к нему
сразу (`VENA_HELPDESK_URL=http://helpdesk:8090`, токен `VENA_HELPDESK_TOKEN`, по умолчанию
`local-helpdesk-token`). Пустое значение `VENA_HELPDESK_URL=` отключает экспорт.

```bash
curl -H 'Authorization: Bearer local-helpdesk-token' http://localhost:8090/tickets
```

`GET /equipment` отдаёт реестр из `emulators/helpdesk/fixtures/equipment.json` в формате
коннектора учётной системы, с пагинацией по `cursor`: 17 каналов демонстрационного снимка
с объектом, секцией, производителем, моделью, серийным номером и датой установки.
Синхронизация с ним в compose выключена: она добавляет каналы эмулятора в реестр, а реестр
публикуется в справочник ML (`справочник_каналов_датчиков.csv` в `VENA_DATASET_DIR`).
Включайте её только на стенде без реального справочника:

```bash
VENA_EQUIPMENT_SYNC_ENABLED=true docker compose up -d backend
```

Канал, уже загруженный из справочника с другим внешним идентификатором, не перезаписывается:
синхронизация отклоняется целиком, а реестр остаётся прежним.

Тесты эмулятора: `cd emulators/helpdesk && pytest` (нужны fastapi, httpx и pytest, например
из окружения backend).

## LDAP / Active Directory (ТЗ 11)

```dotenv
VENA_LDAP_ENABLED=true
VENA_LDAP_URL=ldaps://dc.example.local:636
VENA_LDAP_BIND_DN=CN=vena-reader,OU=Services,DC=example,DC=local
VENA_LDAP_BIND_PASSWORD=replace-on-server
VENA_LDAP_BASE_DN=OU=Users,DC=example,DC=local
VENA_LDAP_USER_FILTER=(|(sAMAccountName={login})(userPrincipalName={login})(mail={login}))
VENA_LDAP_USERNAME_ATTRIBUTE=sAMAccountName
VENA_LDAP_ID_ATTRIBUTE=objectGUID
VENA_LDAP_GROUP_ROLES={"CN=Vena-Admins,OU=Groups,DC=example,DC=local":"admin","CN=Vena-Dispatchers,OU=Groups,DC=example,DC=local":"dispatcher","CN=Vena-Viewers,OU=Groups,DC=example,DC=local":"viewer"}
VENA_LDAP_DEFAULT_ROLE=none
VENA_LDAP_GROUP_SCOPES={"CN=Vena-ODS,OU=Groups,DC=example,DC=local":["all"],"Vena-Alpha":["complex:5"]}
VENA_LDAP_DEFAULT_SCOPES=["all"]
VENA_LDAP_CA_FILE=/srv/certs/customer-ca.pem
VENA_LDAP_TIMEOUT_SECONDS=5
```

OpenLDAP: обычно USERNAME_ATTRIBUTE=uid, ID_ATTRIBUTE=entryUUID,
USER_FILTER=(|(uid={login})(mail={login})). Группы читаются из memberOf: для OpenLDAP
нужен memberOf overlay. Маппинг использует прямое членство, не вложенные группы AD.
Без совпадения применяется DEFAULT_ROLE; `none` запрещает вход. Внутри совпавших
групп выбирается наибольшая роль. Административные права не берутся из запроса клиента.
Области видимости групп суммируются при каждом входе; см.
[authentication.md](authentication.md#области-видимости).

После настройки перезапустите backend: на экране входа появляется выбор
«Корпоративный LDAP / AD», `/auth/status` возвращает ldap_available=true.
Это признак полноты настройки, а не обещание доступности сервера каталога.
`POST /auth/ldap` принимает login/email и password. Выполняются поиск служебной
учётной записью, затем bind найденного DN паролем пользователя. Пустой пароль,
неоднозначный результат, отключённый AD-пользователь и неверный пароль отклоняются.
LDAP-фильтр экранируется. `ldap://` обязательно использует StartTLS до bind,
`ldaps://` — TLS сразу. Проверка сертификата/имени обязательна, небезопасного
отката на открытое соединение нет. Служебной учётной записи достаточно чтения.

Создаётся отдельная запись `ldap:<login>` с устойчивым ID каталога; локальные
аккаунты по совпадению email не объединяются. Пароль каталога не сохраняется.
JWT, защищённая cookie, ограничение попыток и выход работают так же, как локально.
Роли обновляются при входе; блокировка в самом каталоге действует на новые входы.
Уже выданный JWT действует до истечения VENA_JWT_TTL_MINUTES или локальной блокировки.
Для немедленного отзыва заблокируйте пользователя в Vena. Пароли LDAP и группы
меняются на стороне каталога; локальный сброс для них запрещён.

Необходимы доступ сервера Vena к корпоративной сети (при необходимости VPN),
адрес/DC, доверенный CA, base DN, служебный bind и согласованные группы.
Без этих данных проверка настоящего AD заказчика невозможна. Тот же код проверяется на
тестовом каталоге OpenLDAP: профиль `ldap` корневого compose, [authentication.md](authentication.md#тестовый-каталог-ldap).

Параметры TLS сверены с документацией [ldap3](https://ldap3.readthedocs.io/en/latest/ssltls.html) и [OpenLDAP](https://openldap.org/doc/admin26/tls.html). В изолированном OpenLDAP проверены LDAPS, StartTLS, отказ при неверном пароле и недоверенном сертификате. Проверка корпоративного AD требует его адреса и учётной записи.

## Пользователи

**Настройки → Пользователи**: создание локальных аккаунтов, блокировка/разблокировка,
роль, сброс пароля. Любое изменение доступа отзывает существующие сессии.
Нельзя заблокировать себя, понизить свою роль или отключить последнего администратора.
События попадают в аудит; пароли не возвращаются API и не журналируются.
На стенде user1 назначен администратором; остальные демонстрационные аккаунты — диспетчеры.

## Лента событий на главном экране

В API-режиме «Пульс» получает данные из `GET /api/v1/events/recent?hours=6`.
Лента показывает события принятого CSV/XLSX и потока СМВУ, названия каналов и
`ид_объект` из реестра. Окно отсчитывается от последнего события журнала; дата
показана явно, поэтому исторические данные не выдаются за текущую телеметрию.
Обновление — каждые 10 секунд. Без данных выводится приглашение к загрузке.
Синтетическая лента и автоматическое создание демонстрационной карты в production отключены.

Поток сохраняется в БД и очереди публикаций одной транзакцией. Повторный `event_id`
с теми же полями пропускается, с другими — отклоняется (409). В ответе
`last_event_count` — число новых принятых событий. После фиксации транзакции
фоновый процесс передаёт события в ML; при сбое операция повторяется.
